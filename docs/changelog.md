## [Unreleased]

### Added
- **The reply suggester (prd phase 2 §4A, build step 2).** A candidate writes; a few seconds later the matchmaker has one to three drafts waiting above the composer, in their own voice, each with **Send**, **Edit** and **Dismiss**. *Why:* this is the feature phase 2 exists for — the rest of it is the machinery that makes this one trustworthy.
  - **The agent is briefed once, then kept up to date.** A conversation gets one `@convex-dev/agent` thread, and the thread is the memory. The first turn carries everything: the matchmaker's voice, the candidate's whole profile, the recent messages. Every turn after it carries only what has changed — the new messages, a voice that has been rewritten, profile entries that have moved, each marked as replacing what it was told before. `conversations` keeps three high-water marks (`agentBriefedSeq`, `agentBriefedVoiceAt`, `agentBriefedProfileAt`) so the delta is computable; re-sending the world every message would pay twice for what the thread already holds, and bury the new message under text the model has read four times.
  - **It is shown everything the matchmaker knows, their own notes included.** The earlier guardrail said the agent must never *see* that; it now says it must never *repeat* it. A drafter working from half the file writes worse drafts, and a note like "would introduce to Jordan first" is exactly what makes a good next question — while writing it back to the candidate would be a betrayal of the person who wrote it. The control is that nothing reaches anyone until a human presses Send. The seeded standing instruction says all of this in those terms, and the test that pinned the old wording now pins the new.
  - **Everything the matchmaker touches is on the record; the drafts are rows.** `replySuggestions` persists each one, so they survive a reload and going stale is a state rather than a guess. Four of them: `ready`, `stale` (the thread moved, or they replied in their own words), `sent`, `dismissed`. Nothing is deleted — what was offered and passed over costs less to keep than to explain later.
  - **Sending one is sending a message.** It goes out under their name, in the ordinary thread, and the candidate cannot tell. `messages.source` gains `ai_suggestion`, which records how the message started and not who is answerable for it. An edit is still a suggestion: the draft is what got them there. Sending one retires the alternatives, because that is what they were.
  - **Edit does not answer the card.** It drops the text into the composer and leaves the draft on offer, so changing your mind gives you the original back — and it never writes over a half-typed message, which is the one thing it must not do.
  - **Debounced, not per keystroke.** A message schedules a run ~5s later and cancels the one already pending, so a burst of typing is one generation. The matchmaker's own reply schedules one too: what they wrote is the best evidence of how they write, and the agent should have it before the next message rather than after.
  - **Three deployment settings, none of which can take the feature down**: `AI_REPLY_DEBOUNCE_SECONDS`, `AI_REPLY_COUNT`, `AI_REPLY_LIVE_WINDOW`. Unset falls back, nonsense falls back, out of range clamps — a typo in an env var is not a reason for a matchmaker to lose their drafts (prd §9.2).
  - **Every way out is quiet.** Agent unconfigured, switched off, no model, no gateway, thread moved on, model refused or failed — all end with no drafts, which is the phase-1 app working exactly as it did. A failure to draft must never be a failure to send.
  - **Not streamed yet.** prd §4A asks for `persistent-text-streaming` and a sub-2s first token; this generates complete drafts and writes them as rows. The table and the cards do not move when streaming lands — it is a change to one action.
  - **Where it lands.** A `convex/replySuggestions/` domain rather than inside `messages/` as prd §8 sketched: it owns a table, a registry of what gets sent, and its own write path, which is what `CLAUDE.md` §8 means by a domain. `rules.ts` has no Convex imports, so every word that leaves this deployment is unit-testable and readable in one file.
  - **Tests:** 28 unit cases over the briefing and the deltas — what the opening brief carries, that an update carries only what moved, that a rewritten voice is re-stated, and the forgiving parse of what comes back; 17 convex-test cases over the debounce collapsing a burst, staleness on both sides, sending as written and edited, the alternatives retiring, tenancy from three directions, and a run with no agent doing nothing quietly; and 7 Playwright cases driving Send, Edit and Dismiss against seeded drafts. **The generation itself has no e2e coverage and cannot have any:** the gateway needs a paid Convex Cloud deployment and the suite runs on a local anonymous one, which is also why `scenario.replyDrafts` exists.

- **The match board, and a deterministic matching algorithm behind it (prd phase 3 §2, §4, §5).** A new page at `/app/mm/:username/matches`: five columns — Suggested → Reviewing → Introduced → Mutual interest → Connected — with **Rejected as a lane under them rather than a sixth column**, because a rejection is not the last stage of a match but the end of one. A nightly cron scores every pair in every book and puts what it finds in Suggested. *Why:* phase 1 and 2 gave a matchmaker somewhere to keep what they know about people; this is the first thing the product does *with* it.
  - **No AI, on purpose.** The PRD's pipeline is "hard filter on facts → AI compatibility reasoning"; this is the first half, and for now it is the whole of it. Every card is produced by `convex/matches/rules.ts` — plain code, no Convex imports, exported through `@repo/api` so the board renders exactly the reasoning the run recorded. A matchmaker can be told precisely why two people are on a card together, and the same book scored twice gives the same answer twice.
  - **Missing data never disqualifies.** A blank field is something nobody has recorded yet, not a "no". Every hard filter needs *both* halves of itself on the record before it fires, and each is mutual: gender against what each of them is looking for, age against each stated range, height, the registry's own word `dealbreaker` for children, "a partner having children is fine", and a required shared religion. A partner who merely *should* want children is a preference, so it scores badly and blocks nothing.
  - **Every score is symmetric, because a pair is unordered.** The two ids are stored sorted and `pairKey` is the pair itself, unique across the table — which is what stops tonight's run suggesting the same two people last night's did, and makes "are they already on the board?" one indexed read. One-sided preferences are evaluated both ways and averaged.
  - **A score is only as good as its coverage.** Two near-empty profiles agree about everything: they score 100 and still don't reach the board, because the score is the weighted mean over the signals that *could* be read and `coverage` says how much of the possible weight that was. A card needs 50 and 35% coverage, both named constants in one file. The board shows them together — "82 — on a full profile" — so a number is never offered on its own.
  - **A card leads with why, including why not.** The run stores the signals it read, and the card shows the strongest few *plus the weakest one when it is genuinely weak*: "Both want marriage · Both in Toronto · Smoking: never and regularly". A card that listed only what agrees would lie by omission, and the one axis where two promising people don't line up is the thing a matchmaker most needs to see. Free-text `dealbreakers` are flagged rather than read — no algorithm here understands them, and the card says so instead of implying they were checked.
  - **The nightly run never reopens a decision a person made.** It only revises its own untouched `suggested` cards: a rescoring is patched quietly (the profile change behind it is already in the trail, and a nightly event per card per book would bury the events that matter), while a card it *withdraws* — the pair has become impossible, or fallen below the bar — is audited, lands in the Rejected lane, and is marked `rejectedBy: "system"`, the one rejection nobody chose. Running it twice in a row changes nothing the second time.
  - **The run keeps the board in step with the book, not only with the profiles.** A suggestion whose pair it never looked at — somebody left, was archived, or had their profile emptied — is taken back with "one of them is no longer in your book", keeping the score it had while they were both in it. A board should not be offering an introduction that can no longer be made.
  - **One transaction per book, fanned out by the cron.** A single transaction covering every tenant would be one read limit away from a night where nobody gets any matches, and one slow book away from delaying the rest. Twenty new cards per book per run, so a matchmaker opens a shortlist rather than a list; the rest wait for tomorrow and the run says how many it held back.
  - **The same pass runs on demand.** "Find matches" runs it now, as the matchmaker, and reports what it looked at as well as what it found — "Looked at 12 profiles, 66 pairs · 4 new suggestions". An algorithm that only speaks at 3am can't be learnt from, and "nothing new" means something completely different over sixty pairs than over one.
  - **Everything a card can do is a command as well as a drag.** Cards are `draggable` and columns are drop targets, but every move is also in the card's menu — not a fallback, but the same command in a second place, because a board that could only be driven by dragging is one half the people who need it can't use. The Rejected lane is reachable only through a form that takes **who and why**, both required: that reason is the taste signal the board exists to collect, and a dropdown of five reasons would have collected five reasons. Moving a card back onto the board clears the rejection, because a stale reason is worse than none.
  - **Two yeses, held as sub-state.** An introduced card carries each side's answer as the matchmaker heard it, and recording the second yes advances the card to Mutual interest in the same mutation — that transition *is* the two yeses, and having to also drag the card would be a second way of saying it, and a way of being wrong about it. **Nothing reaches a candidate:** the introduction moment is still undesigned (§6), and a set of buttons in their chat would have been the design.
  - **Manual pairing produces an identical card**, `origin: "manual"`, scored by the same algorithm — *including* a pair the hard filters refuse, which is the point of having it: a matchmaker who has met both of them knows something the profiles don't. The card still says what the algorithm thought, and the audit event says the pair was made against it.
  - **Every stage change is audited on both candidates' trails**, as two events, with `relatedEntityId` pointing at the other person so a reader can follow the card back. A trail is read one person at a time, and an event filed under only one of them would leave the other's history missing the introduction they were half of. Six new audit actions, a `matches` entity table, and a **Matches** filter on the History tab — which also meant teaching `audit/rules.ts` to render a stored `mutual_interest` as the label the board uses.
  - **Deviations from the phase 3 draft, all deliberate:** `origin` is `algorithm` rather than `ai`; `rejectedBy` gains `system`; `reasoning` (AI prose) becomes `signals`, the arithmetic the run actually did; `pairKey` answers the draft's open question about one match per unordered pair; and the Rejected lane's ageing period is a month, in the view only — the row and its reason stay for good.
  - **The dev seed now has a book worth matching.** Four more joined members with filled-in profiles, plus facts on the three who already existed: between them a pair the algorithm is confident about, a thin one, and pairs the filters refuse outright. The seed then runs the *real* pass and moves three cards along, because a seeded board the nightly run could never have produced is one you can't learn anything from.
  - **The brand gives way in the header inside a workspace.** One more nav link was one too many at 390px; the workspace's own nav is where you are and where you can go, and the name of the product is neither.
  - **Tests:** 61 unit and convex-test cases for the algorithm and the mutations — symmetry, unknown never disqualifying, each hard filter, coverage refusing a thin pair, idempotence, the run leaving touched cards alone, a withdrawal, tenant isolation, the fan-out — plus 20 for how a card reads, and nine Playwright cases in `app-convex/matches.spec.ts` driving the board end to end against a real backend. The scenario builder can now seed cards at any stage, since the run itself can only ever produce `suggested`.
- **The dev seed writes profiles, so the suggestion cards have something to show.** `seed/dev` predated `candidateProfiles` and wrote none at all, which meant a local `pnpm dev` could not display the stack above the composer at all — the one surface with no way to reach its own state by clicking, because only an agent opens a proposal and none runs yet. *Why:* a feature you cannot see locally is a feature nobody will notice is broken.
  - **Sam Candidate carries four open proposals**, one of each way a card can read: a value where nothing was recorded (`locationCity`), one that replaces what is there (`lookingFor`, `unsure → long-term`), one asking for an entry to go (`pets`), and a free-text note. So the row has arrows and a `1/4` counter. **Jordan Member carries one**, so the same row appears without either — a different card, worth seeing beside it. **Alex Member carries none.**
  - **Every quote is something the candidate actually says in the seeded thread**, so the verbatim line under a proposal is checkable rather than lorem. `sourceQuote` is now seedable in the e2e scenario builder too (`quote`), and `chat-suggestions.spec.ts` asserts it renders — it was reachable only from an agent before, which is to say from nowhere.
  - **Maya's own voice gets a draft waiting on it**, so the "Suggested change to your profile" row is present in *every* conversation until it is answered. That is the correct behaviour rather than a seeding accident: it is about the matchmaker, not whoever they happen to be reading.
  - **Additive one entry at a time, not one row at a time.** These people are seeded long before anyone clicks on them, so by the time a proposal is added to the fixture they already have a profile — and both a `continue` on the candidate and a guard on the profile row would have meant no proposal was ever written again. An entry already on the record keeps its value, its source and its timestamp, and only gains a `pending` if it has none; an entry that is not there is created; a proposal already open is left alone. Nothing is overwritten, which is also why a proposal you have answered comes back on the next seed: from the seed's side that is indistinguishable from one that was never written. The same rule covers the matchmaker's voice. The candidate, conversation and message writes moved into `seedMember` to make the split legible.

- **Suggestion cards above the message composer (prd phase 2 §5).** What the assistant is asking the matchmaker now sits at the bottom of the conversation, between the thread and the input: **one row per kind, and at most one card per row**. Four kinds are named and ordered in `apps/app/src/chat/suggestions.ts` — a suggested match, a change to the matchmaker's own profile, a change to the candidate's, and a drafted reply, the last of these nearest the box being typed in. *Why:* a proposal about someone is worth answering where the conversation that produced it is, and the candidate panel is behind a toggle on anything narrower than `lg`.
  - **A row is a carousel, not a pile.** The newest card shows; arrows either side step through the rest and stop at the ends rather than wrapping, with a `2/5` counter so the position is legible without counting. A row holding one card has neither. Left and Right do the same from the keyboard for anyone whose focus is inside the row, which is a `fieldset` for its native `group` role rather than a `div` wearing one.
  - **Dismiss answers the card showing and only that one.** The selection moves *before* the mutation runs: the query drops the answered card on its own, and a row that waited would fall back to the newest and move a card out from under whoever had arrowed to it. Answering the last card of a row steps back rather than emptying the screen.
  - **Two of the four rows have a source today**, and both of them already existed: the open `pending` proposals on this candidate's `candidateProfiles` entries, and the one open on the matchmaker's `voice`. Accepting or dismissing goes through `resolveSuggestion` / `resolveVoiceSuggestion`, so it is audited exactly as it is from the panel. The reply suggester (prd §4A) and the matcher (phase 3) are rows the stack already orders and nothing yet fills — when either lands it is one more `push` in `chat/conversation-suggestions.tsx` and no change to the stack.
  - **The same proposal is answerable in two places**, which prd §5 asks for: the panel's Profile section and this stack. Either one resolves it and the other stops showing it. How a change *reads* — `no → yes`, `Remove this — A cat`, the verbatim quote under it — was lifted into `workspace/profile-proposal.tsx` so the two surfaces cannot drift apart.
  - **Presentation is separate from data.** `chat/suggestion-stack.tsx` takes cards and knows nothing about Convex; `chat/suggestions.ts` is the grouping and selection logic with no React, unit-tested (14 cases) rather than driven through a browser. Six Playwright cases in `app-convex/chat-suggestions.spec.ts` cover the row-per-kind layout, the arrows stopping at both ends, a dismissal leaving its neighbours alone and surviving a reload, an acceptance reaching the profile, and the voice draft answered from the conversation.

- **The notifications panel is real: it reads the backend (`notifications.queries.feed`).** The bell shipped a week ago on a fixed sample; that sample is gone, and `useNotifications` is now a query and one mutation. What it shows: conversations with messages past your read marker, candidates who joined or left in the last month, and invitations waiting for your address — merged newest-first, capped at 20.
  - **Derived on every read, not stored.** There is no feed table and nothing writes a feed row: the panel is a projection of `conversations`, `candidates` and their read markers, so it cannot disagree with the workspace beside it. A stored "you have unread messages" is a copy that can be wrong, and the one thing worse than a missing notification is one for a message that isn't there. It costs a handful of bounded indexed reads, all through existing indexes but one — `candidates.by_matchmakerId_and_membershipChangedAt`, so recent joiners don't mean reading every candidate a matchmaker has.
  - **One item per conversation, and never the message.** Five messages from one person are one line that says "5 new messages". §8's rule — who wrote, never what they wrote — was written for lock screens and inbox previews, and it holds here too; a convex-test and an e2e spec both assert the body never reaches the panel.
  - **Opening the bell is not reading the message.** "Read" for the panel is one watermark per account, `notificationSettings.feedSeenAt`, set by `markFeedSeen` when the panel opens. The conversation's own marker still only moves when the thread is open (§8.1), so glancing at the bell quiets the bell and nothing else: the workspace keeps its unread count, and a push or email already scheduled still fires. This is the question the UI left open, answered — the badge means "new since you last looked", not "unread messages".
  - **A third channel §8 didn't name.** It has push's and email's rules but neither of their costs, so it deliberately skips their machinery: no delay, no coalescing table, no throttle. A membership change stops being news after a month, because nothing ever "reads" an acceptance and a quiet workspace's panel would otherwise be a list of who joined it last year. An invitation has no window — it is waiting on an answer for as long as it is open, and it expires on its own.
  - **Both sides of the product, one account.** A matchmaker who is also somebody else's candidate gets all three sources merged; a candidate who left is told nothing, the same rule the send path applies.
  - **The row is a real link again.** It was Base UI's `Popover.Close` rendering one, which stamps button semantics onto whatever it renders — the console said so under test. The panel is now controlled and closes itself on navigation, so the row is a plain `<Link>` that opens in a new tab like any other. `PopoverClose` is gone from the UI kit rather than left as a trap.
  - **The PRD now names three channels, not two.** §8 was written for push and email; the panel is neither, so it had no rules to inherit and none of its decisions were written down anywhere but here. New §8.3 says what it is derived from, why seen is not read, and why it has no switch, no delay and no throttle; sign-in moves to §8.4.
  - **Tests:** 16 convex-test cases for the query — both sides, coalescing, the private note that notifies nobody, reading clearing an item, the watermark being per account, signed out, and one account never seeing another's — plus rules tests for the ordering, the cap and the window. `specs/app-convex/notifications-panel.spec.ts` drives the loop end to end: someone writes, the bell counts it, opening quiets the bell while the workspace still says the message is waiting, and following the item lands on the thread.

- **`candidateProfiles` and `matchmakerProfiles`, replacing `notes` (prd phase 2 §3).** The matchmaker's record of a person becomes a structured document: `facts` keyed by a registry of ~48 typed fields, and `notes` keyed by whatever anyone names. The matchmaker's own profile gets the same treatment with one field so far — their `voice` — edited at `/app/mm/:username/settings`. *Why:* phase 2 needs somewhere for an agent to put what it learns, and "who is allowed to change this" has to be a property of the data rather than a convention each caller remembers.
  - **One document per candidate, not one row per fact.** This replaces the `facts` table the PRD had specified. Every value carries who wrote it, when, from which message, and whether a proposal is waiting on it — forty typed columns would have been forty nested objects, and adding a field would have been a schema migration every time. The registry in `convex/candidateProfiles/rules.ts` holds the types instead, so adding a field is an edit to one file. The cost is that a stored value is a string; it is a *normalised* one, because `valueError` then `normaliseValue` is the only way a value reaches the database, from a matchmaker's form and from an agent alike.
  - **The history of a value is the audit trail**, which was being written anyway. No supersession chain, no `status` column: the trail is already append-only and already refuses to be rewritten, and a second copy of that history would be less trustworthy than the one that doesn't. Which entry moved is `changes[].field` — `facts.wantsKids`, `notes.idealWeekend` — rendered through the registry so the History tab says "Wants children" and not a key.
  - **Three ways a value gets written, declared per field in the registry** (`matchmaker` / `agent` / `suggest`), not per matchmaker and not by a confidence threshold. `matchmaker` is the matchmaker's own judgement (`incomeBand`, `matchmakerNotes`); `suggest` is the special categories and anything a wrong guess costs a real person (`orientation`, `religion`, `politics`, `ethnicity`, `drugs`, `dateOfBirth`, and `voice`). A note key nobody has named defaults to `suggest`.
  - **This replaces the auto-apply confidence threshold in prd §9.2.** A model's confidence is not calibrated across fields: a threshold would have let a bad 0.9 on `orientation` through while blocking a good 0.7 on `pets`. `confidence` is still stored, to show and to tune against.
  - **An agent never overwrites what a person typed**, whatever the policy says — an `agent` field whose current source is `matchmaker` degrades to a proposal. One rule, enforced in one function (`agentWriteMode`), for a candidate's birth date and a matchmaker's voice alike.
  - **A proposal sits beside the value, never instead of it**, and there is at most one open per field. A later run that has learnt something better replaces it rather than queuing behind it, and the superseded one is audited rather than vanishing. A proposal can be a **removal** as well as a value, because an agent learns that something has stopped being true as often as it learns what is — and `value: ""` could not say so, since an empty value already means "nothing recorded". Writing a value does **not** answer an open proposal (whoever wrote it may never have seen it); writing exactly what it proposed, or removing an entry it proposed removing, does.
  - **Approving makes the value `agent_approved`, not `matchmaker`.** They agreed with it, they did not write it — so a later agent run may revise its own work, and still never theirs.
  - **Three directories, not two.** `convex/candidateProfiles/` and `convex/matchmakerProfiles/` each own a table and its functions; `convex/profiles/` registers no functions at all and holds the entry type, the validation and the write engine. One more directory than `CLAUDE.md` §8's one-per-domain, and the honest shape: the rule about who may write what has to mean the same thing in both.
  - **The agent's door is built and nobody has come through it.** `applyAgentEntries` and `applyAgentVoice` are internal mutations with no caller; the extraction that will feed them is prd §8 step 3. The caller says what it noticed and does *not* say whether to write or to suggest — an agent that could choose would make the policy advisory.
  - **A fourth writer is deliberately absent rather than stubbed:** a candidate editing their own profile (prd §9.3) would be one more `ProfileWriter` and one more policy in the registry, and nothing else would move.
  - **Erasure reaches it.** `anonymiseCandidateProfile` replaces the identifying and special-category facts the registry marks `personal` — birth date, city, occupation, orientation, religion — and leaves the rest standing, exactly as `status` and `membership` survive in the trail. Free-text notes are **not** redacted, on the same grounds phase 1 left note and message bodies alone: they are the matchmaker's own words, and whether a request reaches into them is the controller's call.
  - **UI:** the candidate panel's Notes section becomes **Profile**, rendering what is filled in rather than forty-odd empty rows, grouped by the registry, each value with its source and its verbatim quote, and an inline editor whose control comes from the field's value kind. Suggestions sit above the record and look unlike it. The History tab's Notes filter becomes **Profile**, and still covers the `note.*` events the old table left behind.
  - **A new `agent` variant of `auditActor`**, carrying the model it ran on — "the assistant changed this" is only half an answer once the model behind an agent has moved on.
  - **Tests:** 62 new unit and convex-test cases covering the policy engine, every value kind's validation and normalisation, the registry's own consistency (no duplicate keys, every group renders, every `choice` option is a value the field would accept back, the special categories are all `suggest`), all four write outcomes, a bad generation being dropped while the rest of its batch lands, a suggestion superseding a suggestion, every way a proposal can be resolved, removals under each policy, and the erasure. Two Playwright specs — `app-convex/candidate-profile.spec.ts` and the voice arc in `matchmaker-profile.spec.ts` — drive the whole thing through the UI, including a proposed removal.
  - **`notes` is gone, in one change rather than three.** A one-off internal mutation folded the surviving rows into a `notes.matchmakerNotes` entry, oldest first, and deleted them; removed notes stayed removed, because the History tab already records that they were removed. Prod held no rows and dev's two were migrated before the table came out of `schema.ts`, so the usual widen → migrate → narrow collapsed into a single commit — which is only safe because there was no third deployment to be out of step. The `note.created` / `note.edited` / `note.removed` audit actions stay in the vocabulary, and under the new **Profile** filter: the trail is append-only, so events written before the change still have to read.

- **A notifications overlay under the bell in the header — the UI only, on a fixed sample.** A panel anchored to the bell rather than a side drawer: a notification is read in passing and then acted on or ignored, so it should sit over the page for a second and leave. A drawer asks the page to move aside, which is the right gesture for something you work *inside* (the candidate panel) and the wrong one for a list you glance at. Full-width-minus-a-gutter at 375px, capped at 22rem and 60vh above that.
  - **`NotificationsMenu` (`apps/app/src/notifications/notifications-menu.tsx`) is a pure view.** It takes a list and one callback, `onOpen`, and owns nothing: what a notification *is*, when it becomes read and where it goes are the caller's. A row with an `href` is a link that closes the panel on the way out; one without is plain text rather than a control that looks clickable and isn't.
  - **Opening it is what marks everything read**, so there is no "mark all read" button — looking is the only thing that button ever meant. What the panel *shows* deliberately doesn't follow: the dots are snapshotted as it opens and held while it is on screen, because otherwise every dot vanishes under the cursor of the person who opened it to see which ones were new. The bell goes quiet immediately, which is the honest answer to "is there anything I haven't seen".
  - **`useNotifications` is the seam, and today it lies.** It returns four fixed items so the UI could be built and judged before there is anything to read. **Wiring means replacing that hook's body** — a query for the list and a mutation behind `markAllRead` — and deleting the sample; nothing above it changes. Until then the bell shows the same three unread to every signed-in person, so this must not ship to a real deployment as it stands.
  - **The badge stops counting at 9+, the label doesn't.** Three digits in a 1rem circle say nothing, but "Notifications, 12 unread" is exactly what a screen reader should hear — so the badge is `aria-hidden` and the count lives in the button's name. Unread is a dot *and* a heavier title, because weight alone isn't available to everyone.
  - **`Popover` joins the UI kit** (`packages/ui/src/components/popover.tsx`), beside `Menu`: a menu holds items you pick one of, a popover holds a panel with structure — a heading, a list, a button of its own. Portalled, with collision padding so a panel anchored top-right doesn't run off a phone.
  - **Tests:** unit tests for the unread count, the badge's ceiling, the unread snapshot outliving the read it describes, the short ages (`now`/`5m`/`3h`/`2d`/a date, with the year once it's another one) and initials. `apps/e2e/page-objects/app/notifications.page.ts` carries the selectors; there is no spec yet, because with a fixed list there is nothing a test could change.

- **AI agent settings come from the database and nowhere else (prd phase 2 §4.4).** There are no defaults in the code: `convex/ai/rules.ts` holds validation and labels and no prose at all, and nothing substitutes a model or an instruction at generation time. An agent nobody has configured is simply **off**. *Why:* a default in the code is a value that runs in production without anyone having chosen it, and the first person to read the module is the first to find out.
  - **A switch per agent**, plus **empty means off** for the model and the instruction. So there are four ways to be off — never set up, switched off, no model, no instruction — and the page says which one rather than just "off". `activeAgent()` is the single question a feature asks: it returns the settings or `null`, so no caller has to remember the four conditions.
  - **The starting values are seed data, not defaults** (`convex/seed/ai/fixture.ts`, applied by `ai:setup`). - **Three AI agents, and a page to tune them (`/admin/ai`, prd phase 2 §4.1, §4.4).** The five jobs the PRD had listed collapse into three agents — `conversation` (drafts a reply, notices facts, keeps the thread summary), `candidate_profile` and `voice_profile` — each with one model and one standing instruction, stored in the database and editable by a platform admin. *Why:* the five-job split put two agents on the read side and left the write path to a record as a step rather than an owner; three agents separate proposing from writing.

### Added
- **Erasure requests (`/admin/erasure`):** the resolution of the one place where "nothing is deleted" (prd §6) and a right-to-erasure request genuinely conflict. ### Changed
- **One Doppler project for every app:** `matchmaker_app` and `matchmaker_www` are merged into a single `matchmaker` project, with one branch config per app under each environment (`dev_app`, `dev_admin`, `dev_www`). `doppler.yaml` binds each app directory to its config, and `apps/e2e/doppler.ts` now takes the app name and builds `<environment>_<app>`; `E2E_DOPPLER_CONFIG` is replaced by `E2E_DOPPLER_ENVIRONMENT`. *Why:* the Doppler workplace is at its project limit, and a project per app would not leave room for the admin app. Values shared by every app can now live in the root `dev` config and be inherited. Rerun `doppler setup --no-interactive` in every checkout and worktree after pulling.
- **Sign-in emails come from `no-reply@aileenlancif.com`** (was `no-reply@matchmaker.io`). *Why:* Resend only sends from a verified domain, and `matchmaker.io` isn't ours. `aileenlancif.com` is the interim production domain and is verified in Resend.
- **`pnpm dev` serves both frontends from `https://matchmaker.localhost`:** the marketing site at `/` and the app at `/app/`, mirroring production's one-origin layout (before: `www.matchmaker.localhost` and `app.matchmaker.localhost/app/`). Portless routes by hostname only, so the app's Vite server now runs as `matchmaker` and, only under portless (`PORTLESS_URL`), proxies every path outside `/app` to the Next dev server at `www.matchmaker.localhost`, including Next's HMR websocket. Bare `/app` redirects to `/app/`, and `matchmaker.localhost` joins Next's `allowedDevOrigins`. *Why:* the site's `/app/` links now work in dev, and dev shares cookies and storage the way production does. The e2e suite is unchanged: it runs Vite without portless, so no proxy.
- **Marketing site (`apps/www`) rewritten against the phase-1 spec (`prd/`):** *Why:* the site described the old single-file PRD — email threads, per-matchmaker sending domains, AI drafting the first email — none of which is in phase 1.
  - **How it works** is now the invitation flow: the matchmaker clicks Onboard and enters the candidate's email (name, social handles and the pasted DM history optional; the history is visible only to them) → the candidate gets an invitation from `invites@matchmaker.io` or a shareable invite link → they sign up, accept, and the conversation continues in the app's chat.
  - **Email is no longer described as a conversation channel.** Gone: reply-by-email, "one thread across channels" and "sent from your domain" (feature card and FAQ). A new FAQ answer says email only carries sign-in codes, invitations and content-free new-message notifications.
  - **"Clients" are now "candidates"** throughout the copy.
  - **AI is framed as coming next.** The six feature cards now cover only phase 1 (one chat per candidate, imported DM history, invite by email or link, notes and change history, notifications, mobile), and suggested replies and the self-building profile move to a dashed "Coming next" callout (`data-testid="coming-next"`). The principles ("We organise. You decide.") and FAQ are rewritten the same way.
  - **Hero illustration** no longer shows an auto-applied fact or a suggested reply. It shows the pasted Instagram history marked "Only visible to you", the invitation being accepted, the chat and composer, and the candidate panel's History tab.
  - **Privacy copy** drops "only used to find matches" (phase 3) and adds that nothing is deleted: the matchmaker keeps the conversation and notes if a candidate leaves or deletes their account, and candidates are told so before accepting.
  - Removed the leftover `/.clerk/` entry from `apps/www/.gitignore` (auth is Convex Auth).
  - e2e: `page-objects/www/landing.page.ts` gains `getComingNext()`. `specs/www/landing.spec.ts` updates the mock and FAQ assertions and adds tests for the invitation flow and for keeping AI out of the feature cards.
- **HTTP routing (`convex/http.ts`, `convex.config.ts`):** the app's router now owns the whole `.convex.site` URL space. Auth discovery is at `/.well-known/…`, HTTP actions at `/api/…`, and the two static sites are registered as catch-alls (`/app/…`, then `/`) instead of being mounted with `httpPrefix`. The health check moved to `/api/health` (same URL as before). The app's Vite `base` is now a fixed `/app/` rather than `STATIC_HOSTING_BASE_PATH`. *Why:* Convex validates Convex Auth's tokens through an OpenID discovery document that has to sit at the site root, and the `customJwt` alternative rejects tokens without a `kid` header.
- **Interim production domain: `www.aileenlancif.com`.** The production deployment will be served there with the existing path-based layout (`/`, `/app/`, `/api/`), and the apex redirects to `www`. PRD §10 records the decision and README → *Custom domain* has the DNS and Convex steps. *Why:* the PRD's `matchmaker.io` is taken and no product domain has been bought yet; this gets a real HTTPS origin now without blocking that choice.
- **e2e runs in several worktrees at once without colliding** (`docs/e2e-architecture.md` §1c). Parallel agents each work in their own git worktree and may all run the suite at the same time. Each run now brings up its own Vite, Next and Convex backend, and nothing is shared between them:
  - **Convex ports are allocated per run** and passed to the CLI with `--local-cloud-port` / `--local-site-port`. `scripts/convex-local.mjs` writes them into the worktree's `config.json` before starting. Before, a worktree's recorded port could be held by a sibling's backend. Every anonymous deployment is named `anonymous-agent`, so the CLI mistook the sibling for its own backend and refused to start.
  - **All ports come from 20000–32000, via `scripts/pick-ports.mjs`, instead of `listen(0)`.** Port 0 draws from the OS's ephemeral range, which outgoing connections also use. With two suites running, `next dev` hit `EADDRINUSE` on a port the allocator had just released. Next also binds `127.0.0.1` explicitly now.
  - **One backend per worktree** (`packages/api/.convex/e2e-backend.lock`). A second run in the same checkout fails straight away instead of starting a second backend on the same SQLite file or wiping the database mid-run. The Convex webServer is no longer reused (`reuseExistingServer: false`). A stale lock left by a killed run is taken over once its holder is confirmed dead.
  - Verified with two worktrees, one with no deployment yet: three rounds of both suites at once, 21/21 each time. Also tested: both worktrees recording the same port (both passed) and two runs in one worktree (the second was refused, the first passed).
- **e2e app servers run under Doppler:** `apps/e2e/doppler.ts` wraps the Vite and Next `webServer` commands in `doppler run --project matchmaker_{app,www} --config dev`, so the suite gets the same env as `pnpm dev`. Variables the harness sets itself (`VITE_CONVEX_URL`, `NEXT_PUBLIC_CONVEX_URL`, `NEXT_DIST_DIR`) are passed to `--preserve-env`. By default Doppler would override them with the *cloud* Convex URL, and the suite would then talk to your cloud deployment while seeding the local one. `E2E_DOPPLER=0` runs the servers without Doppler (CI sets it: CI has no Doppler token), and `E2E_DOPPLER_CONFIG` selects a different config.
- **The e2e `www` server now gets a Convex URL from the harness**, the same local or placeholder URL as `apps/app`. Before, it relied on `apps/www/.env.local`: a fresh checkout failed env validation, and a filled-in one pointed the site under test at a cloud deployment.
- **`apps/www` is a static export:** `output: "export"`, `trailingSlash: true`, unoptimised images, and `manifest.ts` marked `force-static`. The Clerk middleware (`proxy.ts`), Clerk provider and sign-in/up buttons are gone — a static site has no server to run them — and "Get Started"/"Sign In" now link to `/app/`, where auth will live.
- **`apps/app` builds with `base: "/app/"`** (overridable by the static-hosting CLI's `STATIC_HOSTING_BASE_PATH`); the service worker registers from `BASE_URL` and caches `./` rather than `/`. The e2e `app` projects navigate to `/app/`.

- **`apps/app` uses `@vitejs/plugin-react` instead of `@vitejs/plugin-react-swc`:** *Why:* Vite 8 (Rolldown) warns that the SWC plugin is slower when no SWC plugins are configured, and none are; `plugin-react` does Fast Refresh through Oxc there. Build, typecheck and e2e unchanged.

### Fixed
- **Blank page at `/app` without a trailing slash in production:** the app's router basename was `/app/`, which the bare `/app` doesn't match, and production serves that path without redirecting (dev redirects it, so this only showed up in prod). The basename is now `/app`, which matches both.
- **`convex dev` / `convex deploy` failed typechecking `convex/auth.config.ts`** (`Cannot find name 'process'`). Convex typechecks `convex/` without Node's types, so the file now reads `CONVEX_SITE_URL` through the generated, typed `env` from `_generated/server` (which is `process.env` at runtime), like the rest of the backend.
