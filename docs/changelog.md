# Changelog

All notable changes to this project will be documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.0.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added
- **A theme control in `apps/app`:** light, dark, or whatever the device says, cycled from one button in the header and remembered per browser. An inline script in `index.html` applies the stored choice before first paint, so a dark-theme user gets no flash of the light palette.
- **The candidate panel (phase 1 step 6):** the workspace's right-hand column, with Details, Notes and History (`apps/app/src/workspace/candidate-panel.tsx`). It sits beside the thread from `lg` up and takes the column on anything narrower, with its own Close button — the thread's header, which holds the toggle, is hidden while it's open. *Why:* everything the matchmaker knows about a candidate that isn't the conversation.
  - **Details:** the matchmaker's own label for them and their social handles, saved with the server's rules; their email, how they accepted, and their membership; and the status (active, paused, archived) that drives the list's filters. Their email isn't editable here — while invited it belongs to the invitation, and once joined it's the address they accepted with.
  - **Notes:** add, edit and remove, each audited. Removing is soft, like everything else.
  - **History:** the audit trail, newest first, paged, with the spec's filters (All · Details · Invitations & membership · Notes). Sentences come from `audit/rules.ts`, so what is shown is what was recorded, and each entry names who did it — "You", the candidate, System, or a platform admin.
  - **Seeded worlds now carry their membership history** (invitation created, then accepted, declined or left), so a seeded candidate's History reads like a real one's.
  - `Tabs` in `packages/ui`, on Base UI. The selected tab is marked `data-active`, not `data-selected` — worth knowing, since the wrong one fails silently.
  - **Tests:** convex-test for notes, details, status and the history query (including its filters and refusals), and `specs/app-convex/candidate-panel.spec.ts` for the three tabs, validation, and the panel collapsing on a phone.
- **Chat (phase 1 step 5):** both sides now hold one conversation, live. *Why:* this is the product — everything before it was getting a candidate into a thread.
  - **Real-time both ways** through Convex subscriptions: a message appears on the other side with no refresh, proven in the e2e suite by driving two browser sessions at once.
  - **One sequence per conversation**, allocated server-side (`messages/helpers.ts`), so ordering can't race. Sending moves `lastSeq`, `lastPublicSeq` (only for messages the candidate can see), `lastMessageAt`, and the sender's own read marker.
  - **Private messages** keep the "Only visible to you" treatment and never reach the candidate: their thread reads through the `by_conversationId_and_visibility_and_seq` index, which can't return anything else.
  - **Read markers** (`markRead`, `markReadAsCandidate`) move forward only, and never past what that side can see, so a stale or hopeful client can't rewind them or mark unseen messages read. The app reports them while the conversation is open *and* the tab is visible (prd §8.1), which is what step 8's notifications will skip on.
  - **Unread counts** in the workspace list, straight from the conversation's counters — no scan.
  - **Paged scrollback** (30 at a time, `usePaginatedQuery`) with "Load older messages", and the thread follows new messages unless you've scrolled up to read.
  - **The composer** is open only while the candidate is a member, enforced in the mutation as well as the UI; before and after, the thread stays readable. Enter sends, Shift+Enter starts a line, and text survives a failed send.
  - **The candidate's chat** at `/c/:matchmakerUsername` is now a real thread with a composer, not a placeholder.
  - **Tests:** convex-test for sequencing, private-message isolation, membership gating, validation, read-marker clamping and unread counts; `specs/app-convex/chat.spec.ts` covers live delivery between two sessions, unread badges, paging, the closed composer and keyboard sending.
- **`pnpm test:e2e:observe`:** runs the e2e suite headed, in one worker, with a 500 ms pause between actions (`E2E_SLOW_MO` overrides it) and stretched timeouts. *Why:* watching a flow run is the quickest way to see what a spec actually does, and the normal run is far too fast to follow.
- **Per-spec-file test data for the e2e suite (`apps/e2e/scenario.ts`, `convex/seed/e2e/scenario.ts`):** a spec file seeds its own accounts, profiles, candidates, threads and invites in `beforeAll`, under a namespace unique to that file and run, and asserts only on what comes back. *Why:* specs used to build their data by clicking through the UI, which is slow and can only reach the states the UI reaches. Scenarios can seed an expired invite (with a real, openable link), someone who left a month ago, or an invitation already emailed three times today, and seeded rows carry the audit events the product would have written.
- **HTTP sign-in for specs that aren't about signing in (`apps/e2e/session.ts`):** `signInAs()` runs the real Convex Auth email-code flow over HTTP and writes the session to `localStorage` once, before the page loads. About ten times faster than typing a code, with no inbox polling to flake, and signing out still really signs out. The sign-in and admin specs still drive the UI.
- **Accessibility scans (`apps/e2e/a11y.ts`, `specs/app-convex/accessibility.spec.ts`):** axe-core (WCAG 2.1 A/AA) over every screen in a real state — sign-in, home, create profile, workspace, conversation, invite controls, onboard form, settings, accept screen, candidate chat. All clean today.
- **Tenant isolation and phone-layout suites:** `specs/app-convex/tenant-isolation.spec.ts` goes straight to URLs a rival matchmaker, a candidate, a stranger and a signed-out visitor must not reach, and checks private history and notes never appear; `specs/app-convex/mobile.spec.ts` re-runs the main flows at 380px and fails on any sideways scroll.

### Changed
- **The candidate panel uses collapsible sections instead of tabs** (`Accordion` in `packages/ui`, on Base UI). *Why:* a matchmaker reading a thread wants the details and their notes at once, not one at a time. Several sections can be open together; Details starts open.
- **Dark mode can now actually be chosen.** The tokens only defined their dark values inside a `prefers-color-scheme` block, so forcing `.dark` did nothing on a light device. The dark palette is now defined once as `--dark-*` and applied by the media query *or* a `.dark` class. Caught by a screenshot, not by the first test — which is why the theme spec now asserts the rendered colour, not just the class.
- **The app header gives way at phone width.** The new control pushed "Sign out" past a 380px viewport; the brand and workspace name shrink instead.
- **CI no longer runs the e2e suite.** `.github/workflows/ci.yml` is lint, typecheck and build only; the `e2e` job is gone, along with the `E2E_CONVEX=0` / `E2E_DOPPLER=0` and placeholder-URL environment it needed. *Why:* the job had been failing on every push. Standing a browser suite up on a cold runner, with no Convex backend and no Doppler token, meant it could only ever exercise statically-rendered chrome — a permanently red build that told us nothing a local `pnpm test:e2e` doesn't. Run the suite locally before pushing; putting it back in CI means giving it a real deployment first (`docs/e2e-architecture.md` §2, §8).
- **The e2e suite runs tests within a file serially, and files in parallel** (`fullyParallel: false`). *Why:* tests in a file can then share the world it seeded without racing each other, while files stay independent through namespacing. Convention: keep a spec file under ~10 tests, split by flow.
- **`invites.queries.preview` takes the viewer's clock** so an invite that expired before its scheduled job ran reads as invalid instead of offering Accept. Display only: `accept` and `decline` still check the server's clock, so a wound-back `now` only shows a screen that then refuses.
- **Platform admin app (`apps/admin`, served at `/admin/`):** a third Vite + React SPA on the same origin and Convex deployment as the product app, registered as an `admin` static-hosting instance in `convex/convex.config.ts` / `http.ts` and shipped by `pnpm ship`. Who may use it comes from the deployment: sign-in is the same email + code flow as the app, and `convex/admin/helpers.ts` then checks the caller's **verified** address against the comma-separated `PLATFORM_ADMIN_EMAILS` env var (unset means nobody). Every function in `convex/admin/` starts with `requirePlatformAdmin`, so the UI gate is a courtesy and the server is the enforcement. *Why:* support work — reading the audit trail and signing in as an account to reproduce a problem — had to be done from the Convex dashboard, untraceably.
  - **Audit trail** (`/admin/audit`): every matchmaker's events, newest first, filtered by matchmaker (and one of its candidates) *or* by the account that acted, and by action, with the filters in the URL so a view can be shared. Each combination has its own index on `auditEvents` (`by_candidateId_and_action`, `by_matchmakerId_and_action`, `by_actor_userId`, `by_actor_userId_and_action`, `by_action`), so no filter scans; asking for a tenant *and* an account at once is refused rather than served by a scan. Rows name the actor, matchmaker, candidate and the account an account-level event is about, and clicking any of them narrows the view.
  - **Sign-in codes** (`/admin/sign-in-codes`): finds an account by the start of its email and issues a six-digit code for it, written straight into Convex Auth's `authVerificationCodes` in the shape its email provider verifies. The code is returned to the admin, never emailed to the account's owner, replaces any unused one, and is audited as the new `account.sign_in_code_issued` action with the admin as the actor (a new `platform_admin` role on `auditActor`). Deleted and never-signed-in accounts are refused.
  - **`I already have a code`** on the app's sign-in page (`apps/app`): goes to the code step without sending a code, which is how an issued code is spent — "Email me a code" would replace it. The provider id is now shared as `SIGN_IN_PROVIDER_ID` from `@repo/api` rather than repeated as a string.
  - **Separate sessions on one origin.** The admin app gives `ConvexAuthProvider` its own `storageNamespace`, so signing in to `/app` as someone else with an issued code doesn't take over the admin session in `/admin` (they share `localStorage`).
  - **Dev:** `apps/admin` runs under portless at `https://admin.matchmaker.localhost`, and `apps/app`'s Vite server — the front door at `https://matchmaker.localhost` — now proxies `/admin/` to it (HMR websocket included), so dev keeps production's one-origin layout. `doppler.yaml` binds `apps/admin` to a `dev_admin` branch config in the `matchmaker` project; create it and run `doppler setup --no-interactive` again to pick it up.
  - **Tests:** convex-test suites for the admin rules, queries (filters, labels, refusals) and the code mutation; Vitest for the app's filter and label helpers; and two new Playwright projects, `admin` (no backend) and `admin-convex`, with page objects in `apps/e2e/page-objects/admin/`. The seed gains two platform admins, a code target, a non-admin, and a `matchmaker.created` event per seeded profile; `PLATFORM_ADMIN_EMAILS` is set per run by `apps/e2e/auth-env.ts`. `specs/admin-convex/sign-in-codes.spec.ts` issues a code, spends it in a second browser context pointed at `apps/app`, and checks the trail recorded it.
- **Invitations (phase 1 step 4):** onboarding now emails the invite, and people can answer it. *Why:* an invite is how a candidate record gets linked to a real account.
  - **The email** ("<Matchmaker> invited you to Matchmaker" plus the link, sent as `"<display name>" <invites@aileenlancif.com>`) goes out from a scheduled action, through Resend or, without a key, to the internal outbox. The token is re-derived in the action from the invite's nonce rather than passed in, so it never sits in the scheduler's stored arguments. A send scheduled for an invite that has since been replaced, answered or revoked does nothing. Links are `SITE_URL/invite/<token>`.
  - **The accept screen** at `/invite/:token` (the link works for any signed-in account; a signed-out visitor signs in and comes back) and at `/invitations/:candidateId` (home-page invitations, only for the verified invited address). It shows the matchmaker's name and the privacy notice, then Accept or Decline. Accept links the account, marks the candidate `joined`, uses up the link, and opens `/c/<username>`, which is a shell until chat lands in step 5. Used, revoked and expired links all say only "This invitation isn't valid any more".
  - **Refused, invite left open,** when the account owns the matchmaker profile, is already a member, or is linked to an older record in the same book (someone who left). The last case is a decision beyond the PRD: accepting would give one person two records with one matchmaker, so the matchmaker re-invites the old record instead.
  - **The matchmaker's banner** on an invited conversation now has **Resend** (3 emails a day per candidate, counting the first; counted from the audit trail, exact because mutations are serialisable), **Change email** (new token at the new address, so the old link dies; an address already in the book links to that candidate), and **Revoke**. Declined, departed and expired invites show when it happened and **Re-invite** (`membership.reinvited`). A candidate who accepted from a different address shows "Invited as … · Accepted as …".
  - **Expiry after 30 days** is a scheduled job per invite, which only clears the invite it was scheduled for. It hops at most 20 days at a time: JavaScript timers overflow past about 24.8 days, and convex-test runs the scheduler on them.
  - `AGENTS.md` §8 gains an `actions.ts` role for domains that call out of Convex (email now, LLMs in phase 2). `email/helpers.ts` has a generic `sendEmail`, and `emailOutbox.kind` gains `invite`.
  - **Tests:** convex-test for the whole lifecycle (email and link, accept by link and from the home page, the three refusals, expiry and the stale-job guard, decline → re-invite, the resend limit, revoke, change email) and the email's content and sender escaping. `specs/app-convex/invitations.spec.ts` runs the matchmaker and the candidate in two browser contexts and reads the links from the outbox (`apps/e2e/invite-emails.ts`).
- **Onboarding candidates (phase 1 step 3):** the workspace's **Onboard** button opens a form for the candidate's email, an optional name, social handles and the pasted DM history. Submitting writes, in one mutation (`candidates.mutations.onboard`), the candidate (`invited`, `active`), its conversation, the history as a private message at the start of the thread, an open invite, and the `candidate.created` / `invite.created` audit events. The matchmaker then lands in the new conversation. *Why:* this is how a candidate relationship moves from the DMs into the app.
  - **The same email twice** (any case, any membership state) writes nothing, and the form links to the existing candidate. Onboarding never reads `users`, so it behaves the same whether or not the email has an account (prd §9.1).
  - **Copyable invite links.** The token is HMAC-SHA256 of a per-invite nonce under a deployment secret (`INVITE_LINK_SECRET`, `convex/invites/helpers.ts`). Only the nonce and the token's hash are stored, so the database alone can't produce a working link, yet the owner can copy the same link again at any time (`invites.queries.token`). Set the secret once per deployment with `pnpm --filter @repo/api invites:setup [--prod]`; the e2e harness sets its own each run. *Why:* the spec stores only a hash but also wants **Copy invite link** at any time, and a hash alone can't rebuild the link.
  - **Handle rules** (`convex/candidates/rules.ts`, shared with the form): profile URLs and "@" are stripped for Instagram, TikTok and X. WhatsApp is stored as E.164 and must include the country code; a "(0)" trunk prefix and a leading "00" are handled, but a local number is refused, never guessed.
  - **Workspace:** the candidate list (most recent first, status filter, search by name or email, Invited/Declined/Left/Account deleted markers) and a read-only conversation view. Private messages are marked "Only visible to you". An invited candidate's conversation shows the invite banner with the link and **Copy invite link**. On a phone the conversation replaces the list, with a way back. A malformed or foreign conversation id shows "Conversation not found".
  - **UI:** `Textarea` and `NativeSelect` in `packages/ui`, both on Base UI's `Field.Control`.
  - **Tests:** convex-test suites for the rules, the invite tokens, onboarding (atomic writes, duplicate, no account lookup, tenant isolation, missing secret) and the list, conversation and token queries. Vitest for the app's label helpers, and `specs/app-convex/onboarding.spec.ts`. Shared e2e sign-up helpers now live in `apps/e2e/accounts.ts`.
- **Matchmaker profiles (phase 1 step 2):** any account can create a matchmaker profile at `/mm/new`, linked from the home page until the account owns one. *Why:* every later phase-1 step (onboarding, chat, the candidate panel) happens inside a matchmaker's workspace.
  - **Username rules** (`convex/matchmakers/rules.ts`, exported through `@repo/api` so the form checks exactly what the server does): 6–30 letters, digits and periods, no leading, trailing or doubled period, at least one letter, and the reserved list from `prd/phase-1.md` §1.2. Uniqueness is on the canonical key with dots removed, as in Gmail, so `jane.smith` is refused once `janesmith` exists.
  - **Backend:** `matchmakers.mutations.create` and `update` (display and business name; the username never changes), audited as `matchmaker.created` / `matchmaker.updated`. `matchmakers.queries.workspace` resolves a URL's username in any case or dot placement, and returns `null` alike for a profile that isn't yours and one that doesn't exist, so the URL can't be used to probe for usernames. `profileHistory` lists the profile's own audit events.
  - **App:** `/mm/:username` opens the workspace shell (candidate list and conversation column; a phone shows only the list). Other dot placements redirect to the chosen form. `/mm/:username/settings` edits the display and business names and shows the profile's history. The candidate panel and the Onboard button come with steps 3 and 6.
  - **Tests:** convex-test suites for the rules, mutations and queries (including a stranger being refused), Vitest for the app's history sentences and error helper, and `specs/app-convex/matchmaker-profile.spec.ts` with page objects in `page-objects/app/matchmaker.page.ts`.
- **Test accounts for the dev deployment (`convex/seed/dev/`):** `pnpm --filter @repo/api seed:dev` adds six `@matchmaker-dev.test` accounts: a matchmaker (Maya, owns `maya.matches`), three joined candidates (Sam has a short thread that includes a matchmaker-only message), one invited person, and one blank account. `seed:dev:code <email>` prints that address's latest sign-in code from the outbox. The seed only adds what's missing and never wipes, so it's safe to re-run. It refuses to run unless `SITE_URL` is on `.localhost` and `RESEND_API_KEY` is unset, so it can never touch prod. *Why:* dev had no data, and exercising the matchmaker, candidate and invite flows needed an account in each state.
- **Sign-in with Convex Auth (phase 1 step 1):** email + six-digit code, one flow for sign-in and sign-up (`convex/auth.ts`, `apps/app` `/sign-in`), then a name step for new accounts. A custom `createOrUpdateUser` (`users/helpers.ts`) keeps one account per email and never reuses a deleted account. Codes go out through Resend when `RESEND_API_KEY` is set; otherwise they're logged and written to an internal `emailOutbox` table, which is how local dev and the e2e suite sign in. `pnpm --filter @repo/api auth:setup` sets a deployment's signing keys. *Why:* the PRD moves auth from Clerk to Convex Auth and uses codes rather than magic links, which break in installed home-screen apps.
- **Phase 1 schema and foundations (`packages/api/convex/`):** every phase-1 table (users with soft deletion, matchmakers, candidates (which also carry the open invitation), conversations, messages, notes, audit events, notification tables). Also the access helpers `requireUser`, `requireMatchmaker` + `assertSameTenant` and `requireCandidateSelf`, and the append-only audit trail (`audit/rules.ts` action list, `recordAudit`). `users.setName` is audited at account level and fanned out to each joined matchmaker's trail. *Why:* every later step builds on these, and tenancy and audit are easier to enforce from day one than to retrofit.
- **App shell (`apps/app`):** React Router, a sign-in gate on every route but `/sign-in` (with a safe `?next=` return path), and a home page listing invitations, owned matchmaker profiles and joined matchmakers. Vitest for app utilities.
- **Shared UI primitives (`packages/ui`):** design tokens (`@repo/ui/theme.css`, the marketing site's palette) and Base UI–based `Button`, `Field`/`Input`, `CodeField` (OTP) and `Card`.
- **E2E auth support (`apps/e2e`):** global setup gives the local backend fresh auth keys each run, specs read codes from the outbox (`sign-in-codes.ts`), and there are new sign-in, sign-up and home specs with page objects. See `docs/e2e-architecture.md` §1d.
- **Marketing site for Matchmaker (`apps/www`):** replaces the turbostack template page with a landing page built from the PRD — hero with an illustrated product still (a client thread showing an auto-applied fact and a suggested reply), the problem today, how it works (paste the DM → approve the first email → one thread), six features, the "AI drafts, you decide" principles, privacy and tenant isolation, a FAQ (Base UI Accordion) and a waitlist form. New warm ivory/claret palette in `globals.css` tokens (light and dark) and an Instrument Serif display face (`--font-display`). *Why:* the site described a monorepo template, not the product. Pricing is left out on purpose: the PRD defers billing, so the FAQ says pricing comes later.
- **Waitlist backend (`packages/api/convex/waitlist/`):** a `waitlist` table (indexed `by_email`) and a public `waitlist.mutations.join` mutation that validates, normalises and dedupes on email. It returns `null` whether or not the address was already on the list, so the endpoint can't be used to check who signed up, and a repeat sign-up only fills in fields that were blank. `internal.waitlist.queries.list` pages sign-ups for the dashboard/CLI; nothing public reads them. Validation rules live in `waitlist/rules.ts` with no Convex imports and are re-exported from `@repo/api`, so the form and the server enforce the same limits. The form also has a honeypot field and a 15s submit timeout, so it can't spin forever while the backend is unreachable.
- **Unit tests for `packages/api`:** Vitest + `convex-test` (`pnpm --filter @repo/api test`), covering the waitlist rules, the mutation (normalisation, idempotency, rejection) and the list query. Runs in Vitest's `node` environment: convex-test's recommended `@edge-runtime/vm` peer made pnpm install a second copy of vitest, which broke `@repo/ui`'s typecheck.
- **Convex backend layout convention** (AGENTS.md §8, kept outside the `convex-ai` block that `npx convex ai-files install` rewrites): one `convex/<domain>/` directory per domain, split into `rules.ts`, `mutations.ts`, `queries.ts` and `helpers.ts`, with tests alongside.
- **Doppler for app env vars:** a root `doppler.yaml` binds `apps/app` to the `matchmaker_app` project and `apps/www` to `matchmaker_www` (`dev` config), and both `dev` scripts now run under `doppler run --`. *Why:* secrets live in one place instead of hand-copied `.env.local` files. The e2e suite uses Doppler too — see *Changed* below.
- **Monorepo from turbostack 4.5.0:** Turborepo + pnpm with `apps/www` (Next.js marketing site), `apps/app` (Vite React app), `apps/e2e` (Playwright), and `packages/{api,ui,analytics,config}`. Renamed to `matchmaker` throughout (package name, portless hosts `www.matchmaker.localhost` / `app.matchmaker.localhost`, page titles, e2e selectors).
- **Hosting on Convex (`.convex.site`) via `@convex-dev/static-hosting`:** two component instances in `packages/api/convex/convex.config.ts` — `www` mounted at `/` and `app` at `/app/` — with the app's own HTTP actions under `/api/` (`convex/http.ts`, starting with `GET /api/health`). `pnpm ship` deploys the backend and uploads both sites; `pnpm ship:preview` uploads both to the dev deployment for a hosted smoke test. *Why:* one origin and one deploy target for backend and both frontends, instead of Vercel. Verified against a local backend: `/`, `/app/`, deep links under `/app/…` (SPA fallback), `/app/assets/*`, and `/api/health` all resolve; unknown top-level paths 404.

### Changed
- **One Doppler project for every app:** `matchmaker_app` and `matchmaker_www` are merged into a single `matchmaker` project, with one branch config per app under each environment (`dev_app`, `dev_admin`, `dev_www`). `doppler.yaml` binds each app directory to its config, and `apps/e2e/doppler.ts` now takes the app name and builds `<environment>_<app>`; `E2E_DOPPLER_CONFIG` is replaced by `E2E_DOPPLER_ENVIRONMENT`. *Why:* the Doppler workplace is at its project limit, and a project per app would not leave room for the admin app. Values shared by every app can now live in the root `dev` config and be inherited. Rerun `doppler setup --no-interactive` in every checkout and worktree after pulling.
- **Sign-in emails come from `no-reply@aileenlancif.com`** (was `no-reply@matchmaker.io`). *Why:* Resend only sends from a verified domain, and `matchmaker.io` isn't ours. `aileenlancif.com` is the interim production domain and is verified in Resend.
- **`pnpm dev` serves both frontends from `https://matchmaker.localhost`:** the marketing site at `/` and the app at `/app/`, mirroring production's one-origin layout (before: `www.matchmaker.localhost` and `app.matchmaker.localhost/app/`). Portless routes by hostname only, so the app's Vite server now runs as `matchmaker` and, only under portless (`PORTLESS_URL`), proxies every path outside `/app` to the Next dev server at `www.matchmaker.localhost`, including Next's HMR websocket. Bare `/app` redirects to `/app/`, and `matchmaker.localhost` joins Next's `allowedDevOrigins`. *Why:* the site's `/app/` links now work in dev, and dev shares cookies and storage the way production does. The e2e suite is unchanged: it runs Vite without portless, so no proxy.
- **Marketing site (`apps/www`) rewritten against the phase-1 spec (`prd/`):** *Why:* the site described the old single-file PRD — email threads, per-matchmaker sending domains, AI drafting the first email — none of which is in phase 1.
  - **How it works** is now the invitation flow: the matchmaker clicks Onboard and enters the candidate's email (name, social handles and the pasted DM history optional; the history is visible only to them) → the candidate gets an invitation from `invites@matchmaker.io` or a shareable invite link → they sign up, accept, and the conversation continues in the app's chat.
  - **Email is no longer described as a conversation channel.** Gone: reply-by-email, "one thread across channels" and "sent from your domain" (feature card and FAQ). A new FAQ answer says email only carries sign-in codes, invitations and content-free new-message notifications.
  - **"Clients" are now "candidates"** throughout the copy.
  - **AI is framed as coming next.** The six feature cards now cover only phase 1 (one chat per candidate, imported DM history, invite by email or link, notes and change history, notifications, mobile), and suggested replies and the self-building profile move to a dashed "Coming next" callout (`data-testid="coming-next"`). The principles ("We organise. You decide.") and FAQ are rewritten the same way.
  - **Hero illustration** no longer shows an auto-applied fact or a suggested reply. It shows the pasted Instagram history marked "Only visible to you", the invitation being accepted, the chat and composer, and the candidate panel's History tab.
  - **Privacy copy** drops "only used to find matches" (phase 3) and adds that nothing is deleted: the matchmaker keeps the conversation and notes if a candidate leaves or deletes their account, and candidates are told so before accepting.
  - Removed the leftover `/.clerk/` entry from `apps/www/.gitignore` (auth is Convex Auth).
  - e2e: `page-objects/www/landing.page.ts` gains `getComingNext()`. `specs/www/landing.spec.ts` updates the mock and FAQ assertions and adds tests for the invitation flow and for keeping AI out of the feature cards.
- **HTTP routing (`convex/http.ts`, `convex.config.ts`):** the app's router now owns the whole `.convex.site` URL space. Auth discovery is at `/.well-known/…`, HTTP actions at `/api/…`, and the two static sites are registered as catch-alls (`/app/…`, then `/`) instead of being mounted with `httpPrefix`. The health check moved to `/api/health` (same URL as before). The app's Vite `base` is now a fixed `/app/` rather than `STATIC_HOSTING_BASE_PATH`. *Why:* Convex validates Convex Auth's tokens through an OpenID discovery document that has to sit at the site root, and the `customJwt` alternative rejects tokens without a `kid` header.
- **Interim production domain: `www.aileenlancif.com`.** The production deployment will be served there with the existing path-based layout (`/`, `/app/`, `/api/`), and the apex redirects to `www`. PRD §10 records the decision and README → *Custom domain* has the DNS and Convex steps. *Why:* the PRD's `matchmaker.io` is taken and no product domain has been bought yet; this gets a real HTTPS origin now without blocking that choice.
- **e2e runs in several worktrees at once without colliding** (`docs/e2e-architecture.md` §1c). Parallel agents each work in their own git worktree and may all run the suite at the same time. Each run now brings up its own Vite, Next and Convex backend, and nothing is shared between them:
  - **Convex ports are allocated per run** and passed to the CLI with `--local-cloud-port` / `--local-site-port`. `scripts/convex-local.mjs` writes them into the worktree's `config.json` before starting. Before, a worktree's recorded port could be held by a sibling's backend. Every anonymous deployment is named `anonymous-agent`, so the CLI mistook the sibling for its own backend and refused to start.
  - **All ports come from 20000–32000, via `scripts/pick-ports.mjs`, instead of `listen(0)`.** Port 0 draws from the OS's ephemeral range, which outgoing connections also use. With two suites running, `next dev` hit `EADDRINUSE` on a port the allocator had just released. Next also binds `127.0.0.1` explicitly now.
  - **One backend per worktree** (`packages/api/.convex/e2e-backend.lock`). A second run in the same checkout fails straight away instead of starting a second backend on the same SQLite file or wiping the database mid-run. The Convex webServer is no longer reused (`reuseExistingServer: false`). A stale lock left by a killed run is taken over once its holder is confirmed dead.
  - Verified with two worktrees, one with no deployment yet: three rounds of both suites at once, 21/21 each time. Also tested: both worktrees recording the same port (both passed) and two runs in one worktree (the second was refused, the first passed).
- **e2e app servers run under Doppler:** `apps/e2e/doppler.ts` wraps the Vite and Next `webServer` commands in `doppler run --project matchmaker_{app,www} --config dev`, so the suite gets the same env as `pnpm dev`. Variables the harness sets itself (`VITE_CONVEX_URL`, `NEXT_PUBLIC_CONVEX_URL`, `NEXT_DIST_DIR`) are passed to `--preserve-env`. By default Doppler would override them with the *cloud* Convex URL, and the suite would then talk to your cloud deployment while seeding the local one. `E2E_DOPPLER=0` runs the servers without Doppler (CI sets it: CI has no Doppler token), and `E2E_DOPPLER_CONFIG` selects a different config.
- **The e2e `www` server now gets a Convex URL from the harness**, the same local or placeholder URL as `apps/app`. Before, it relied on `apps/www/.env.local`: a fresh checkout failed env validation, and a filled-in one pointed the site under test at a cloud deployment.
- **`apps/www` is a static export:** `output: "export"`, `trailingSlash: true`, unoptimised images, and `manifest.ts` marked `force-static`. The Clerk middleware (`proxy.ts`), Clerk provider and sign-in/up buttons are gone — a static site has no server to run them — and "Get Started"/"Sign In" now link to `/app/`, where auth will live.
- **`apps/app` builds with `base: "/app/"`** (overridable by the static-hosting CLI's `STATIC_HOSTING_BASE_PATH`); the service worker registers from `BASE_URL` and caches `./` rather than `/`. The e2e `app` projects navigate to `/app/`.

- **`apps/app` uses `@vitejs/plugin-react` instead of `@vitejs/plugin-react-swc`:** *Why:* Vite 8 (Rolldown) warns that the SWC plugin is slower when no SWC plugins are configured, and none are; `plugin-react` does Fast Refresh through Oxc there. Build, typecheck and e2e unchanged.

### Fixed
- **Blank page at `/app` without a trailing slash in production:** the app's router basename was `/app/`, which the bare `/app` doesn't match, and production serves that path without redirecting (dev redirects it, so this only showed up in prod). The basename is now `/app`, which matches both.
- **`convex dev` / `convex deploy` failed typechecking `convex/auth.config.ts`** (`Cannot find name 'process'`). Convex typechecks `convex/` without Node's types, so the file now reads `CONVEX_SITE_URL` through the generated, typed `env` from `_generated/server` (which is `process.env` at runtime), like the rest of the backend.

### Removed
- **Template demo `messages` table and functions**, and the app's demo message list and its specs. The name is now used by phase-1 chat messages. Existing deployments with demo rows must clear them before the new schema will deploy.
- **Clerk wiring:** `VITE_CLERK_PUBLISHABLE_KEY`, the Clerk README section, and Clerk mentions in CI and turbo config.
- Vercel: both `vercel.json` files, `@vercel/analytics`, the `VERCEL` build-cache input and standalone-output switch. Docker (`apps/www/Dockerfile`, `docker-compose.yml`) and `.gitlab-ci.yml`, which targeted the standalone Next server that no longer exists.
